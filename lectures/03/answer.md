## 宿題

- 取り組んだレベル：基礎 / 実装 / 発展

基礎・実装・発展(a)の3つすべてに取り組み、Omnicampus では最も高い「発展」を選びました。

- やったこと：

基礎では、質問3問を使い、元の設定と変更を加えた設定でそれぞれ2回ずつ `--trace` 付きで実行しました。元のコードと変更したコードを git worktree で分けて並行して試しました。ログは [basic](logs/basic/) にあります。

変更1では INSTRUCTIONS から「必ず search_glossary で用語集を確認する」の行を削除しました。変更2では `search_glossary` の docstring を「用語を1つだけ入れる」から「まとめて入れる」に変えました。変更3では回答の最後に関係する回を示す指示を、確認問題を1問出す指示に変えました。追加の確認（変更4）として、変更1に加えて docstring の「答える前に使うこと」も削除しました。

実装では、承認付きの `save_learning_log(title, content)` を追加しました。題名と本文が空でなければ `learning_log/` に日時と題名を含む名前で保存します。CLI は `DeferredToolRequests` を受け取るとツール名と引数を表示し、実行前に承認を求めるようにしました。テストには API キー不要の `TestModel` を使いました。

発展(a)では、`adk_agent/glossary_agent/` に Google ADK 版を作り、用語検索、講義要約、確認問題のツールを登録しました。`PYTHONPATH=. uv run --with google-adk adk run adk_agent/glossary_agent` で実行し、ツール呼び出しの確認には `--jsonl` を使いました。

- 結果：

基礎の元の設定では、Q1「LoRAとQLoRAの違いは？」は `search_glossary` を `LoRA` と `QLoRA` で2回呼び、`requests=2` でした。Q2「3レベル」は `3レベル` で1回検索し、`requests=2` でした。Q3「RAGとエージェントの違いは？」は `RAG` と `エージェント` で2回検索し、`requests=2` でした。

変更1では検索回数に変化がなく、Q1 の入力は 1436 から 1388 トークン、Q2 は 1023 から 975 トークンになりました。docstring にも検索を促す説明があり、INSTRUCTIONS の他の行も用語集を前提にしていたためと考えました。

変更2では Q1 の検索が `LoRA QLoRA` の1回になり、入力は 1436 から 1131 トークンになりました。ツールの部分一致の作りによって、たまたま両方の定義が返りました。一方、Q3 では最初に `RAG エージェント` で検索しても「AIエージェント」だけが返り、モデルが `RAG` で検索し直しました。run1 は `get_lecture_summary(3)` も呼び、`requests=4`・入力2833トークン、run2 は `requests=3`・入力1679トークンでした。元の2回より呼び出しが増えました。

用語集に RAG は載っていません。`search_glossary('RAG')` は、定義文に「RAG」を含む「ファインチューニング」を返します。元の設定のQ3では、エージェントは用語集にないと伝えず、一般知識で RAG を説明しました。変更2のrun2と変更4のrun1では「用語集に定義はありませんが」と明示しました。

変更3では `make_quiz` が使われました。run1 は検索2回と同じターンで `make_quiz({'lecture': 1})` を並列に呼び、LoRA と関係のない第1回の「システムプロンプト」を出題しました。`requests=2` でした。run2 は検索結果を見てから `make_quiz({'lecture': 2})` を呼び、「PEFT」を出題しました。`requests=3`・入力2509トークンでした。どちらも回答末尾の「関係する回」の表示はなくなりました。変更4でも、Q1 は2回、Q2 は1回検索しました。Q3 は run1 で `RAG`、`エージェント`、`検索`、run2 で `RAG`、`エージェント`、`RAG` を検索し、どちらも計3回・`requests=3` でした。

実装のテストでは、承認前にファイルが作られず `DeferredToolRequests` が返ること、承認すると1ファイル保存されること、拒否すると保存されず文字列の回答が返ること、空の題名を拒否することを確認しました。pytest は 15 passed でした。

実際の Gemini での初回実行では、docstring に「実行の前に利用者の承認を求める」と書くと、モデルはツールを呼ばず、文章で確認を求めて終わりました。docstring を、保存を頼まれたら回答の中で聞き返さずツールを呼ぶ説明に直すと、y では承認待ちの表示後にファイルが保存され、n では保存されず、説明だけが返りました。ログは [approve_y.txt](logs/impl/approve_y.txt) と [approve_n.txt](logs/impl/approve_n.txt) です。保存例は [saved_example.md](logs/impl/saved_example.md) にあります。

ただし、`--trace` の `[usage]` は最後の `run_sync` の分だけで、承認後は `requests=1` と表示され、最初の分と合算されませんでした。また、保存ファイルでは本文側にも見出しがあり、題名が二重になりました。拒否したときにモデルが「保存しませんでした」と言わないこともありました。

Pydantic AI 版では、Agent を作成してから関数を1つずつツールとして登録し、モデルは実行時に指定しました。テスト時には TestModel に差し替えられ、承認付きツールや出力型も Agent に記述しました。一方、ADK 版ではモデル名、エージェント名、指示、ツールのリストを Agent にまとめて指定し、実行は対話型の adk run やセッションの仕組みに任せました。どちらも通常の Python 関数をツールとして使い、docstring と型ヒントが説明文になるため、tools.py はそのまま利用できました。なお、ADK ではエージェントに name が必須で、root_agent という変数名で認識されました。

ADK 版では、3問とも Pydantic AI 版と同じツールと引数が呼ばれました。LLM 呼び出しは各質問で2回でした。回答の内容もほぼ同じで、最後に関係する回が付きました。Q1 の入力トークンは ADK が 540+663=1203、Pydantic AI が 1023 でした。ADK には `--trace` のような表示はありませんが、`--jsonl` で `functionCall` を確認できました。

- 気づき・疑問：

INSTRUCTIONS と docstring はどちらもモデルへの指示として読まれるようでした。片方を削除しても、もう片方が検索を促していると考えられる結果でした。人間が承認することを書くと、モデルが自分で確認するよう求めたため、説明文はモデルにしてほしい行動を記述する必要があると感じました。

検索をまとめる指示で呼び出しや入力トークンを減らせる一方、ツールの実装がまとめての検索に対応していないと、取りこぼしや再検索で呼び出しが増えることがありました。docstring はツールの実装に合わせて書く必要があります。また、並列に確認問題を出すと、それ以前の検索結果を使えず、関係のない回の問題になる場合がありました。

疑問として、用語集にないことを伝えさせるには、指示文を強めるより、`search_glossary` の返り値で完全一致しなかったことを明示する方が確実ではないかと考えました。
