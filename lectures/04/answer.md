## 宿題

- 取り組んだレベル：基礎／発展

基礎と発展に取り組み、Omnicampus では「発展」を選びました。

- やったこと：

演習の STEP 3 で直した `rubric.md` を起点にし、同じ `lectures/04/labels.jsonl` に対して、1 回の実行で 1 つだけ変えて採点しました。比べたのは次の4つです。

起点の設定をもう一度実行しました（同じ設定で結果がどれだけ揺れるかを見るため）。採点のモデルを gemini-3.5-flash に変えようとしましたが、30〜40 秒おきに4回試して4回とも 503（モデルが混み合っている）が返り、採点できなかったので、gemini-3.1-flash-lite に変えて実行しました。判定の順序は、`app/judge.py` の `CriterionVerdict` で `reason` と `verdict` のフィールドの順を入れ替え、判定を先に出させました。出力の JSON で `verdict` が `reason` より先に来ていることを確かめてから、元に戻しました。差分は [hw_order_swap.patch](logs/hw_order_swap.patch) です。採点の指示文（`build_judge` の「reason を先に書き」）と `rubric.md` の「先に理由を書いてから判定を決める」は変えていません。

発展では SWE-bench Verified を選びました（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified ）。最初は GPQA Diamond を考えましたが、Hugging Face のデータセット（Idavidrein/gpqa）は利用規約への同意が必要で、ファイルの取得が 401 になったため、同意なしで公開されている SWE-bench Verified にしました。テスト用の parquet ファイル（500 件）を取得して中身を読み、難易度の異なる4件について、問題文、合格に必要なテスト（`FAIL_TO_PASS`）、正解の修正（`patch`）の大きさを見ました。作成と検証の手順は、OpenAI のブログ「Introducing SWE-bench Verified」（https://openai.com/index/introducing-swe-bench-verified/ ）と、元の SWE-bench の論文（arXiv 2310.06770、https://arxiv.org/abs/2310.06770 ）で調べました。

- 結果：

起点（STEP 3 の実行）は、根拠 9 / 10、分かりやすさ 10 / 10、要確認 0 件でした。同じ設定でもう一度実行すると、根拠が 8 / 10 になりました。#06 の根拠が「宿題の答えとなるコードをそのまま書いている」という理由で fail に変わりました。temperature を 0 にしていても、同じ設定で 1 件の判定が変わりました。ログは [hw_base_rerun.txt](logs/hw_base_rerun.txt) です。

gemini-3.1-flash-lite では、根拠 9 / 10、分かりやすさ 8 / 10、要確認 0 件でした。#04 の分かりやすさを「直接的に回答しており簡潔」として pass にし、冗長さを見逃しました。#08 は根拠と分かりやすさの両方を fail にし、分かりやすさの理由には「役割を逸脱しているため分かりやすさ以前の問題」と書きました。ログは [hw_model_31lite.txt](logs/hw_model_31lite.txt) です。gemini-3.5-flash の 503 のログは [hw_model_flash.txt](logs/hw_model_flash.txt) です。

判定を先に出させた場合は、根拠 9 / 10、分かりやすさ 9 / 10、要確認 0 件でした。不一致は #06 の根拠（理由は「用語集に無い実装の詳細なコードを直接記述している」）と、#08 の分かりやすさの2件でした。#08 の根拠はこの実行では pass で、自分のラベルと一致しました。ログは [hw_order_verdict_first.txt](logs/hw_order_verdict_first.txt) です。

どの設定でも、範囲・ヒント・回の表示は 10 / 10 で、要確認は 0 件でした。

発展の SWE-bench Verified は、GitHub の issue（バグ報告など）と、それを直した pull request の組 500 件です。リポジトリは 12 個で、django 231 件、sympy 75 件、sphinx 44 件、matplotlib 34 件、scikit-learn 32 件などでした。データの `difficulty` 列では「15 分未満」194 件、「15 分〜1 時間」261 件、「1〜4 時間」42 件、「4 時間超」3 件でした。

読んだ4件の要約です。astropy-12907（15 分〜1 時間）は、モデルを入れ子に組み合わせると `separability_matrix` が「入力と出力が分離できる」ことを正しく計算しないという報告です。期待される出力が issue に例で示されているので、astropy のモデリングの仕組みを読めば自分でも直せそうです。正解の修正は 1 ファイル 12 行でした。django-10097（15 分未満）は、URLValidator が URL のユーザー名とパスワードの部分に RFC で禁止された文字（「:」「@」「/」）を通してしまうという報告で、直す場所は正規表現 1 か所です。ただ、合格に必要なテストの名前には、問題文の URLValidator とは別の UsernameValidator のテストが並んでいました。sympy-12489（1〜4 時間）は、`Permutation` を継承したクラスを作っても内部で常に `Permutation` のインスタンスが返るという報告です。問題文が直し方（classmethod を使う）まで示していますが、正解の修正は 1 ファイル 293 行で、内部の呼び出しを全部たどる必要があります。xarray-6992（4 時間超）は、インデックスの作り直しのあとで座標の名前が変数より多くなり、`ValueError: __len__() should return >= 0` が出るという報告です。再現コードは2行ですが、正解の修正は 2 ファイル 202 行で、既存のテスト 945 件も壊さない必要があります。自分には後の2件は難しいと感じました。LLM にとっては、問題文に書かれていない仕様（どの例外を出すか、どの関数を残すか）をテストが要求している場合や、修正が複数の場所に広がる場合が難しいと考えました。

作成の人数と手順は次の通りです。元の SWE-bench は、12 の Python リポジトリから集めた 2,294 件です（論文の要旨）。OpenAI は Python の経験がある 93 人のソフトウェア開発者に依頼し、元のテストセットから無作為に選んだ 1,699 件を確かめました。各件を別々の 3 人が、問題文が曖昧すぎないか、`FAIL_TO_PASS` のテストが正しい解答まで落とさないかを 0〜3 の 4 段階で判定し、3 人のうち最も重い判定を採りました。誰か 1 人でも 2 以上（重大）を付けた件は除いています。参加する開発者は、OpenAI のエンジニアが先にラベルを付けた 50 件でテストを受け、合格した人だけが加わりました。結果として 1,699 件のうち 38.3% が問題文の曖昧さ、61.1% がテストの不公平さで指摘され、68.3% が除かれました。残った中から 1〜4 時間と 4 時間超の件をできるだけ入れ、残りを無作為に選んで 500 件にしています（以上はブログ）。採点はテストで行い、`FAIL_TO_PASS`（直したら通るべきテスト）と `PASS_TO_PASS`（前から通っていて、直しても壊してはいけないテスト）を実行して判定します。LLM による採点は使っていません。

今日の評価セットと比べると、規模は 10 件と 500 件（確かめた候補は 1,699 件）で、問題を作ったのは講師 1 人と、実際の開発者が書いた issue と pull request です。検証は、今日は講師 1 人のラベルを受講生が見比べる形でしたが、SWE-bench Verified はテストに合格した 93 人が 1 件ごとに 3 人で見ています。採点は、今日は人と LLM が T/F を付け、コードで判定するのは「第N回」の有無だけでした。SWE-bench Verified はすべてテストの実行で判定していて、人や LLM の判断は採点に入りません。

- 気づき・疑問：

同じ設定の2回で根拠の一致が 9 / 10 と 8 / 10 に分かれたので、1 回ずつの比較では 1 件の差を変更の効果とは言えません。判定の順序を入れ替えた結果も 1 件の入れ替わりにとどまり、揺れの幅に収まっています。効果を見るには、同じ設定を何回か実行して、項目ごとに判定が割れる回数を数える必要があると考えました。

不一致はほとんどが #06 と #08 に集まり、どれも他の基準で見るべき違反（宿題の答えを書いた、役割を変える要求に従った）を根拠や分かりやすさに持ち込んだものでした。モデルを変えても順序を変えても、この持ち込みは残りました。基準ごとに別々に LLM を呼ぶと持ち込みが減るのかが、次に試したい点です。

SWE-bench Verified でも、人の判断が入るのは採点ではなく、問題そのものが公平かを確かめる段階でした。ブログが除いた理由の多くは、問題文やテストが何を正解とするかを決めきれていないことで、今日の演習で `rubric.md` の「まだ決めていないこと」を埋めた作業と同じ種類の問題だと感じました。ただし、ブログはこのふるい分けが厳しすぎる可能性にも触れていて、3 人のうち 1 人でも重大と付ければ除く方式では、正しい問題も落としている可能性があります。また、残った 500 件の中にも、django-10097 のように問題文とテストの対応が名前からは読み取りにくいものがありました。このテストが本当に問題文と関係するのかは、テストのコードまで読んでいないので確かめていません。
